# Architecture

## Design Philosophy

The helper is built entirely with vanilla Minecraft commands and data packs. No mods, no external libraries, no Java. All logic is expressed in `.mcfunction` files and scoreboard operations.

`datapack/` is the source of truth and is edited by hand. `make package` zips it as-is. The top-level `helper/` tree is an older copy that is not packaged. `gen/mansions_gen.py` writes only to `gen/` for a separate Mansions defense pack and does not generate this pack.

A Python sidecar (`sidecar/`) tails the server log for chat, reads the private-order inbox (`/function helper:w`, `/trigger tom`), and drives the helper over RCON through the `helper:api/*` entry points (see "Sidecar API" below). Naming still uses `helper:lifecycle/apply_bound_name`.

A few files are generated by `tools/datapack_gen.py` (`follow/safe_spot`, `api/internal/org_scan_*`); edit the generator and run `make generate`.

## Module Breakdown

### 1. Combat AI (`combat/`)

The combat system is a hybrid: high-level state machine + lightweight distance-based decision making.

**Targeting:** `combat/pick_seen` picks the nearest threat with line of sight (`combat/los_check`), trying up to 8 candidates. The target is tagged `helper.targeted`.

**Priority:** `combat/defend_owner` prefers `helper.priority_target` (whoever hit the owner, see `trust/detect_attack`), then a hunt target, then hostiles near the owner.

**Actions:** `combat/fight` uses `sword_attack` up close, `mid_range`/`strafe` in between, and `bow_attack` at range. `combat/dodge` raises the shield and sidesteps incoming projectiles.

### 2. Trust System (`trust/`)

Only attacker detection is active: `trust/detect_attack` reads the owner's `HurtTime` and tags the attacker (`mark_attacker`) as `helper.priority_target`.

The perimeter/chest-access trust system was removed. `cmd_trust`/`cmd_untrust` still set the `helper.friend` tag and `trust_level` score, but nothing reads them.

### 3. Chest Organization (`chest/`, `storage/`)

The old base-chest and storage-grid sorting code was never called and has been removed. Chest placement and item deposit now happen in jobs (`jobs/place_chest`, `jobs/dig_deposit`, `jobs/fill_nearest_chest`). `cmd_set_storage` records a storage center that nothing reads yet.

### 4. Auto-Smelting (`smelt/`)

Passive auto-smelting is off. Smelting runs as job 9 (`jobs/smelt_job`), which builds a furnace once at the base (`smelt/build_furnace_once`) and loads it (`smelt/load_for_job`).

### 5. Tree Cutting (`tree/`)

Tree cutting runs as job 5 (`jobs/cut_trees`): `tree_scan` → `fell_tree`/`fell_logs` → `strip_canopy` → `vacuum_logs` → `replant_stump`. The old `tree/` functions were removed.

### 6. Intelligent Mining (`mine/`)

Mining is done by jobs (`jobs/dig_*`, `jobs/break_vein`, `mine/break_here`, `mine/scan_near`); tools are held via `spawn/hold_*`. The old `mine/intelligent_mine` tool-selection path was never called and has been removed.

`/function helper:cmd_scan` calls `mine/locate_ore`, which only probes 4 adjacent blocks (not a 32-block radius).

### 7. Horse System (`horse/`)

Runs every helper tick (`horse/tick`, skipped during hunt job 11).

1. If the owner is riding a `#helper:mounts` entity and the helper is not mounted → `horse/ensure` (mount an existing helper horse or spawn one)
2. If the owner is on foot and the helper owns a horse → `horse/despawn_horse`

### 8. Golem Summoning (`golem/`)

Checks for golem structures every 5 ticks.

**Detection:** Scans the 2x2 block area around each player for:
- Tier 1: 4 stone + pumpkin on top
- Tier 2: 4 iron blocks + pumpkin on top
- Tier 3: 4 netherite blocks + pumpkin + diamond block on top

When detected:
1. Check if player already has a helper (reject if so)
2. Spawn the appropriate tier
3. Consume the golem blocks
4. Bind helper to owner (`OwnerUUID`)
5. Set base to player position
6. Mark owner as friend

## Tick Loop

```
tick.mcfunction (every tick, #minecraft:tick)
├── golem/check_structures (every 5 ticks, every player)
├── as each @e[tag=helper.active] → helper_tick
│   ├── tag owner helper.my_owner, memory/snapshot, chunk forceload refresh
│   ├── lifecycle/ensure_name, jobs/tick (instant jobs 1-4), horse/tick, move/gravity
│   ├── trust/detect_attack, combat/calm_golems, combat/dodge
│   ├── target selection (raid_select / pick_seen / pick_food), combat/defend_owner
│   ├── combat/fight
│   ├── long jobs 5-15 (cut_trees, place_chest, raid, dig, smelt, craft, hunt,
│   │   lay_rails, clear_wall_torches, clear_rails, repair_rails)
│   └── idle: follow/keep_up or combat/idle_behavior (stay / fetch / watch)
├── as @a[helper_want=1] → lifecycle/owner_tick (recall, forceload recovery, respawn)
└── /trigger helper_cmd 1-9 and /trigger tom dispatch
```

The sidecar adds work over RCON through `helper:api/*` only.

## Modes, protection and follow

Two switches per helper, resolved every tick by `combat/apply_mode` (the only place that derives `helper_mode`):

| helper_stay | helper_pf | effective mode | follows | protect reflex | fall recovery |
|---|---|---|---|---|---|
| 1 | any | stay_at_base (`helper_mode` 1) | no, returns to base | off | off |
| 0 | 1 | protect_follow (3) | yes | on | on |
| 0 | 0 | idle (4) / legacy fetch (2) | no | off | off |

Stay-at-base always wins, whatever sets the flags (sidecar, triggers, chat). A staying helper also drops roaming jobs (5, 7, 8, 11-15) if a legacy trigger queues one.

**Protect reflex.** When `#protect` is on and `combat/defend_owner` finds a threat to the owner, `#defending` is set. Any job except the hunt (11) pauses: `combat/preempt_save` remembers the work position and facing, the job dispatch is skipped, the helper warps to the owner if more than 16 blocks away, and fights. When the threat is gone, `combat/preempt_restore` teleports back and the job continues. The cost when nothing is happening is unchanged: one `defend_owner` scan.

**Follow.** `follow/keep_up` walks after the owner and teleports when more than 24 blocks away, in another dimension, or stuck for 20 ticks. `follow/teleport_to_owner` lands on the first spot from `follow/safe_spot`: a fixed list of 36 offsets (same level, then one up, then one down) needing passable feet and head, a non-passable floor, and nothing from `#helper:unsafe_floor` / `#helper:unsafe_body`. If none is safe it lands on the owner.

**Fall recovery.** `follow/fall_check` counts ticks the helper is 3+ blocks below the owner (reset when within 2). At 40 ticks, or at once if 12+ below, it calls `teleport_to_owner`.

## Sidecar API (`helper:api/*`)

Called as `execute as @a[name=<owner>,limit=1] at @s run function helper:api/<fn> {req:<n>,...}`. Every entry point checks the caller owns a helper, that it is loaded, the mode, whether it is busy, and argument ranges. It then writes `storage helper:api result {req, tool, ok, code, msg, job?}`. `api/status` also writes `storage helper:api status` (effective mode, protect/defending/job_paused, job, queue, positions, base).

| function | args | notes |
|---|---|---|
| status | - | snapshot |
| set_protect_follow | on, come_now | come_now refused while staying; recalls if unloaded |
| set_stay_at_base | on | needs a base; cancels work |
| set_base | - | owner position |
| stop_work | - | job + queue |
| gather | resource 1-12, replace | refused while staying |
| dig | blocks 1-2000, keep, store, replace | refused while staying |
| rails | action 1-4, blocks 1-10000, rail_type 0-4, replace | lay / repair / clear_bad / clear_torches |
| craft | item, count 1-64, replace | refused while staying |
| smelt | material 2,3,4,5,11, replace | allowed at base |
| organize_scan | scope 1 ahead / 2 base | base only in stay-at-base |
| organize_apply | scan_req | atomic; see below |
| hunt / raid / store_items | target / replace / replace | owner keyword commands only |

Common codes: `not_owner`, `not_loaded`, `staying_at_base`, `busy`, `bad_args`, `refused` (the legacy starter declined; reason in chat), `no_base`, `not_staying`, `changed`, `bad_plan`, `stale`.

**Chest organizing.** `organize_scan` snapshots up to 8 containers ahead of the helper (3 deep, 5 wide, 4 high) or 24 around the storage point or base (13x6x13) into `helper:api org`. Chests with a loot table are skipped. The sidecar plans the layout in Python (`sidecar/organize.py`) and stages one plan per container. `organize_apply` then does everything inside one function call, so within one tick:

1. Checks every container still exists and holds exactly the snapshot; if not, it writes nothing (`changed`).
2. Builds each new item list by copying items from the snapshot and setting only Slot and count. Slots must be 0-26 and unique, and counts 1-99 (`bad_plan`).
3. Writes the lists.

The planner refuses any plan that does not keep every item total identical. It never merges items whose components differ, and never stacks above the item's real stack size.

## Sidecar tools

`sidecar/tools.py` defines the 12 tools the model may call, each mapped onto one api function. `sidecar/agent.py` runs the bounded loop: one tool call per turn, at most 3 actions and 6 model calls, 20 s. It uses native tool calling, or a strict JSON protocol for models without it. `sidecar/rcon_client.py` keeps one authenticated RCON connection, with reconnect and auth-failure backoff. Tests: `make test`.
